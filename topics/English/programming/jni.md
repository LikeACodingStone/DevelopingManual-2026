# JNI: Calling Between Java and Native Code

- Aliases and ecosystem: Java Native Interface / JNI (Android uses the same specification through the NDK)
- Versions and platforms: the JNI specification of JDK 8 and later; the example targets Linux, and library packaging differs on Android
- Tags: programming
- Example status: not compiled: this machine lacks a JDK and `jni.h`; the check script compiles and runs it automatically when `JAVA_HOME` is set
- Code source: written independently for this handbook; all teaching code is in examples/; no historical project source is referenced

## What it is

JNI lets Java methods call shared libraries written in C/C++, and lets native code call Java. On the Java side you declare a `native` method and load the library with `System.loadLibrary`; on the native side you implement a function whose first parameter is `JNIEnv*`. `JNIEnv` belongs to the current thread and must not be stored across threads.

## When to use

Reusing an existing C/C++ library or reaching platform capabilities. Boundary calls have a cost, so it is a poor fit for frequent fine-grained calls; do not add native code where pure Java will do, because a native bug crashes the whole JVM instead of throwing an exception.

## How to use

1. Declare the `native` method in Java and call `System.loadLibrary("name")` in a static initializer; on Linux this maps to `libname.so`.
2. Generate the C header with `javac -h <directory>` and include it in the native source, so a signature mismatch shows up at compile time.
3. Function names follow the `Java_<package>_<class>_<method>` convention (dots in the package become underscores, and an underscore in a name is written `_1`); you can also register them explicitly with `RegisterNatives` in `JNI_OnLoad`.
4. Build a shared library with header paths `$JAVA_HOME/include` and `$JAVA_HOME/include/linux`; at run time point `-Djava.library.path` at the library directory.
5. Strings: `GetStringUTFChars` returns modified UTF-8 (`U+0000` and supplementary characters are encoded differently from standard UTF-8), and every Get needs a matching Release.
6. Arrays: `Get<Type>ArrayElements` pairs with `Release<Type>ArrayElements`; use `JNI_ABORT` for read-only access to avoid copying back.
7. Exceptions: native code cannot signal Java with a C++ exception; use `ThrowNew` and return immediately, without calling most further JNI functions. After calling a Java method, check with `ExceptionCheck`.
8. References: local references are released when the native method returns; creating many in a loop requires `DeleteLocalRef`; to keep an object across calls you must use `NewGlobalRef` and `DeleteGlobalRef` when done.
9. Threads: a natively created thread must `AttachCurrentThread` before calling Java and `DetachCurrentThread` before it ends.
10. When you keep a native object's pointer in a `long`, you must prevent use after free and double free yourself.

## Minimal example

Run the commands from the handbook root; a JDK is required and `JAVA_HOME` must point at it.

[NativeDemo.java](../../../examples/java/jni/handbook/NativeDemo.java) and [handbook_jni.c](../../../examples/java/jni/handbook_jni.c) show string joining (with a null check), summing an `int[]` (a null array reference and an overflow throw `IllegalArgumentException` and `ArithmeticException` respectively), and keeping a native counter handle in a `long`.

```sh
mkdir -p /tmp/handbook-jni/include /tmp/handbook-jni/classes
javac -h /tmp/handbook-jni/include -d /tmp/handbook-jni/classes examples/java/jni/handbook/NativeDemo.java
cc -std=c11 -Wall -Wextra -Werror -fPIC -shared -I/tmp/handbook-jni/include -I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux" examples/java/jni/handbook_jni.c -o /tmp/handbook-jni/libhandbook_jni.so
java -Djava.library.path=/tmp/handbook-jni -cp /tmp/handbook-jni/classes handbook.NativeDemo
```

Expected: `JNI strings, arrays, exceptions and handles OK`. There is no JDK here and the example was not compiled, so it must not be treated as verified.

## FAQ

- `UnsatisfiedLinkError`: the library name, search path, 32/64-bit, function name or signature does not match; the header generated by `javac -h` can expose signature problems early.
- `FindClass` cannot find an application class in a native thread: it uses the system class loader, so look the class up in a Java thread first and keep a global reference.
- The JVM crashes outright: most often a released reference, an out-of-bounds array access or a `JNIEnv` used across threads.
- On Android, libraries are packaged per ABI and must be built for each target ABI; `System.loadLibrary` likewise drops the `lib` prefix and the `.so` suffix.
- Copying arrays and strings can be expensive; design batch interfaces instead of calling per element.
